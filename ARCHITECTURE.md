# TibDaftari (Clinic-Web) — Architecture & Conventions

React 19 + Vite 8 + TypeScript (strict) + Tailwind v4 + TanStack Query + Zustand + react-router 7 + i18next + motion.

## Layers (dependency direction: top → bottom only)

```
modules/    pages per zone: landing | portal (patients) | staff (/app) | admin (/admin)
features/   feature hooks & feature-level components (react-query hooks, forms, editors)
data/       repository CONTRACTS (repositories.ts) + http impl (http/*.http.ts over http/client.ts)
domain/     pure TS types & pure functions (no React, no I/O)
shared/     ui kit (shared/ui), i18n, theme, lib helpers, hooks, config/routes
app/        router, layouts, guards, providers
```

Rules
- Pages never call `repos` directly for mutations without react-query; use `useQuery`/`useMutation` from a `features/<name>/queries.ts` (or inline in the page if tiny). Query keys: `['<entity>', scopeId, params]` (scopeId = the unit the data is read under).
- Pages never import from `data/http/*` directly. Only `import { repos, ApiError } from '@/data'`.
- All user-facing text goes through `t('ns.key')`. Add keys to `shared/i18n/locales/uz.ts` (base) and mirror in `ru.ts`/`en.ts` (DeepPartial — untranslated keys fall back to uz). Then add the key to the five translated dictionaries `kaa.ts`, `ky.ts`, `tg.ts`, `kk.ts`, `tk.ts` (until then they show it in their fallback language); Uzbek Cyrillic and the new Latin need nothing — they are written from `uz` at runtime.
- Interface languages (`shared/i18n/languages.ts`, ten, each named in itself): Uzbek in three alphabets — `uz-x-yangi` (new Latin of the 2021 draft: ō ḡ ş ç), `uz` (Latin, the source), `uz-Cyrl` — Karakalpak `kaa`, Russian, English, Kyrgyz `ky`, Tajik `tg`, Kazakh `kk`, Turkmen `tk`. uz / ru / en are in the bundle; `uz-Cyrl` and `uz-x-yangi` are made from the Uzbek dictionary by `translit.ts` (letter rules + loanword exceptions; placeholders, `{fields}`, addresses and product names are never touched); the other five are lazy chunks. A missing text falls back to Russian then Uzbek (ky, tg, kk, tk) or Uzbek (kaa). Switch with `setLanguage(code)` (stored in `clinic.lang`; `<html lang>` and `data-script` follow; the app waits under the splash for a lazy language — `i18nReady`). `languages.ts` also says each language's `content` locale — the uz / ru / en the SERVER keeps and writes things in: pass `contentLocale()` (never `i18n.language`) wherever a language is sent or saved (Excel exports' `lang`, a new template's or unit's language, a proposed unit name — `countryLabel(c, contentLocale())`). The platform's default SMS texts (`admin.sms.default*`) are content: every language shows them exactly as its content language has them. Numbers, dates, collation and region names use `intlLocale()` / `DATE_LOCALES` / `collationLocale()` / `regionNames()`. The font follows the language: Onest, and Inter (size-adjusted to Onest, `Inter Ext` in `index.css`) for the letters Onest lacks — the whole interface for uz-Cyrl, kk, ky, tg.
- Colors only via tokens (`bg-surface`, `text-ink-2`, `border-line`, `bg-brand-soft`, `text-danger` …). Never raw hex in components (template documents are the exception — they are printed).
- Use `shared/ui` primitives: `Button, IconButton, Input, SearchInput, Textarea, Select, Checkbox, Switch, Field, Card, CardHeader, Badge, Avatar, Skeleton, SkeletonRows, EmptyState, Stat, Modal, Drawer, ConfirmDialog, toast, Tabs, Segmented, Menu, Pagination, Tooltip, DataTable, Page, PageHeader, Toolbar, Logo, BrandMark, LanguageSwitcher, LanguageName, pickLanguage, ThemeToggle`.
- Permissions: `usePermissions().can('lab.result.write')` or `<Can perm="…">`. Route-level guards already exist in `app/router.tsx`.
- Session: `useAuth((s) => s.staff)` / `useAuth((s) => s.patient)`; scope: `useStaffScope()` → `{ scopeId, facilityId, scopeUnitId }` (the unit chosen in the header and, for reception/lab, the facility under it), `useAdminScope()` for admin pages. Never read `branchId`/`companyId` — they no longer exist. The header picks the scope with `features/org/UnitSwitcher` (levels side by side as columns on wide screens, one column with a path bar on narrow ones; search, recents, keyboard); forms use `UnitPicker`. `features/org/quickstart/` is the «Tezkor ishga tushirish» wizard (`QuickStartDialog`: location → facility → staff → catalogue → review → sign-in sheet) over `repos.org.quickStartPreview / quickStart` — one request creates a facility ready to work (missing region / district nodes, default accounts with one password, the sample facility's catalogue and templates re-bound to the new one, an active cheque); opened from the Units page header and from country / region / district rows.
- Assistant («Yordamchi», `features/assistant/` + `modules/assistant/AssistantPage`, routes `/app/assistant` and `/admin/assistant`, permission `assistant.use`): the chat fills the page over `repos.assistant`; the history of the caller's threads (`ThreadHistory`: search by title, groups by last activity, rename / delete per thread — delete asks first) slides in on a button: pinned beside the chat on a wide screen (the choice is remembered in `clinic.assistant.history`), a drawer over it on a narrow one. The open thread is in the address (`?c=<id>`), so a reload and Back keep it. The model's read tools show as chips, a proposed write renders an `ActionCard` the employee confirms or cancels (`useAssistantActions().resolve`) — nothing runs on the model's word. `Markdown.tsx` renders replies without raw HTML; a file a tool built (`export_data` / `export_table` → Excel / CSV / JSON / PDF / Word / text, `export_document` → Word / PDF / text, `export_chart` → PNG / SVG) shows as a `FileCard` with the kind, one download button (`repos.assistant.downloadFile`, owner-only on the server) and, for pictures, an inline preview fetched with the caller's token. A sent message appears at once as a pending `UserBubble` (replaced by the server's copy when the reply lands) and `Typing` animates while the model works; the composer stays typeable, only sending waits. The waits are kept per thread in the query cache (`useAssistantWorks`, never persisted): the reply and the end of its wait render together, two threads may wait at once, and turns land in the thread the SERVER names. Everything the assistant says between two messages of the employee is one `AssistantTurn` (copy + time); a reply taller than the screen is shown from the question down, otherwise the chat stays at its end. `Composer` grows with the text and carries the working unit, the model and what the role may ask for (`Capabilities`, from `status.tools`); every thread keeps its own unsent draft. Page keys: `H` history, `N` new chat, `/` the composer. What the role may ask for comes from `status.tools` (each with a `group` and `danger`): `Capabilities` lists them by area, the welcome offers only examples the role can run (`EXAMPLES[].needs`), and `status.context` — the working unit's lineage, the same the model is told — shows as a breadcrumb. A proposed write renders its `details` (ids already resolved to names by the server) instead of raw arguments; an irreversible one (`danger`) is red and, when `confirmWord` is set, is confirmed only with that word typed (`repos.assistant.confirm(id, word)`). A question of the assistant (`message.choices`) renders as buttons (`Choices`) — tapping one sends it as the next message while the question is still the last word. While a reply is on its way the send button is «stop» (also Esc and a pill beside the typing hint): `useAssistantActions().stop` asks the server (`repos.assistant.stop`, repeated for a moment until the run has announced itself), the waiting request answers with what was done and a `message.stopped` mark. A done action that left a way back (`action.undo.available`) shows «Orqaga qaytarish» — asked once more, then `repos.assistant.undo`; the card turns to «Orqaga qaytarildi» and the thread gets a note (`message.undoOf`). A pending card says upfront whether the write can be taken back (`action.undoable`). Several writes proposed in one turn (`message.actions`, more than one) share ONE `BatchCard`: rows that open to their details (the one-line summary starts with what tells the rows apart), a tick per row, one «confirm» for the ticked ones (`useAssistantActions().resolveMany` → `repos.assistant.resolveBatch(confirm, cancel)` — the unticked are declined), then every row shows its own outcome and the done ones go back together (`undoMany` → `undoBatch`) or one by one; the per-write chips are not repeated above such a card. Scheduled tasks («Rejali topshiriqlar», `SchedulesPanel` — a drawer opened from the bar's clock button, which counts the active ones, or by `?tasks=1` from a notice): the employee's own list over `useSchedules` (state, rule in the reader's language via `scheduleWhen`, next / last run, why the system switched one off, a switch, run now → its conversation opens, edit, delete) and the form (name, what to do with ready examples, daily / week days / monthly / once, time, a live preview of the rule; the working unit is where a new task runs). A conversation that belongs to a task wears a clock in the history and the title (`threadTitle` drops the «⏰» of its stored name) and a dot while its newest answer is unread (`thread.unread`, cleared by opening it; the list of threads is re-read every minute); the turn a task wrote (`message.scheduled`) renders as a `ScheduledMark`, not as the employee's bubble. A notice whose link starts with `/assistant` opens in the module the reader is in (`AppShell`). Settings → `/admin/assistant-settings` (superadmins only via `RequireSuperAdmin`; no sidebar entry — reached from the assistant page's settings button) (`AssistantAccountCard` with a `target`: for superadmins the PLATFORM account first — provider + key entered once, used by every unit without a closer account (`effectivePlatform`) — then the scope unit's account: inherited / own / off, provider presets for Claude, OpenAI, DeepSeek, Deploy and custom OpenAI-compatible endpoints; the key never comes back).
- Money: `fmtMoney`, dates: `fmtDate/fmtDateTime/fmtRelative`, phone: `fmtPhone` (shared/lib/format).
- Motion: subtle. `Page` already animates entrance. Use `motion` for list stagger (`stagger`/`fadeUp` from shared/ui/Page), hover lift on cards, AnimatePresence for conditional panels. Respect reduced motion (global CSS handles it).
- Large data: tables are server-paginated (`Page<T>` + `Pagination`). Debounce search (`useDebounce`). Keep `pageSize` ≤ 50 by default.
- Files: one component per file, PascalCase for components, camelCase for hooks/utils. Default export only for route pages (lazy-loaded); everything else named exports.
- No `any`. Prefer discriminated unions. Keep components < ~250 lines; split otherwise.

## Domain cheat-sheet
- SMS account (`features/org/UnitSmsAccountCard.tsx`, `domain/org.ts` `UnitSms` / `UnitSmsInput`): a unit's own account is a Xabarchi key (`provider: 'xabarchi'`, `apiKey`, priority) or an Eskiz.uz login (`provider: 'eskiz'`, `login` + `password` + `sender` nick, default 4546); the card shows the provider in effect (own or inherited), the Eskiz note about approved templates, and the test result with the Eskiz balance (`SmsTestResult.balance`). `SmsProvider` = xabarchi | eskiz | none.
- Eskiz extras: `features/org/EskizPanel.tsx` (balance / prices / nicks / templates with moderation state, submit a text; `useEskizInfo`, `useRefreshEskizInfo`, `useSubmitEskizTemplate`), the templates card prices a text with `useSmsCheck` (`POST /units/{id}/sms/check`) and shows the Eskiz moderation state of it (`toEskizTemplate` turns `{x}` placeholders into `%w`); `ComposeDrawer` has a “numbers abroad” switch (country ISO-2 → `countryCode` on the send, Eskiz only); the outbox row shows parts / cost / provider state; Reports › SMS (`features/reports/SmsReport.tsx`, `useSmsReport`, `GET /units/{id}/reports/sms`): KPIs, daily trend, a region → district → facility tree with stacked bars, kinds / providers / operators, CSV + Excel.
- One phone, a whole family (`domain/patient.ts` `Relation`, `RELATIONS`, `FamilyMember`; `features/patients/relations.ts` gender-aware labels + the “Azizaning o‘g‘li” phrase under `relation.*`): `PatientDrawer` splits live duplicates into document matches (open the existing patient) and people on the same number (`FamilyLinkPanel` — open “this one”, or pick who the newcomer is to someone on it; required without passport / PINFL; handles 409 `phone_relation_required` / `duplicate_person`); `FamilyCard` (“On this number”, `usePatientFamily` → `GET /patients/{id}/family`) on the patient page and in reception (pick a member); search rows and the patients list show the relation or “+N on this number”. Portal: `features/portal/family.ts` (`usePortalMember`, `useFamilyView`) + `FamilySwitch` on home / visits / results, rows carry whose they are.
- Organisation (`domain/org.ts`): one tree `OrgUnit` — country → region → district → facility (`level`, `parentId`, `code` = cheque prefix, `settings` inherited down the tree). Helpers `buildUnitTree`, `unitsUnder`, `facilitiesUnder`, `unitAncestors`, `isFacility`. `Employee` (roleId + overrides{allow,deny}, `unitId` home + extra `unitIds`, categoryIds); `Role.scopeUnitId`. System roles: `superadmin`, `installer` ("O‘rnatuvchi" — a superadmin inside the territory a superadmin gave them: home = region or country node, extra = regions of the same country; `isProtectedRole()` — granted/edited by superadmins only), `admin`, `registrator`, `laborant`, `vrach`, `rahbar`, and the read-only leaders `leader_country` / `leader_region` / `leader_district` / `leader_facility` («Davlat / Viloyat / Tuman / Muassasa rahbari» — `LEADER_ROLE_LEVELS`, `leaderLevel()`, `isLeaderRole()`: each pinned to one level of the tree, the employee form limits the home / extra unit pickers to it; after login a leader above the facility lands on `/app/reports`). The session carries `roleName` next to `roleKey` (the top bar shows it). `usePermissions()` → `{ can, isSuperAdmin, isInstaller, canReset }`.
- Platforma (`/admin/platform`, `modules/admin/platform/PlatformPage` → `features/platform/PlatformExplorer`; superadmin — «Platforma», an administrator with reports access — «Hududlar» folded under their own unit): the organisation tree walked from the top, one level at a time — Kompaniya → Davlat → Viloyat → Tuman / shahar → Muassasa. `PathStepper` draws the way (a step taken shows the pick and leads back to that level; the current one counts what there is to choose; below a 64rem container only icons, with the current step spelled out under them). The place is in the address (`usePlatformPath`: `?company=<id>|all&country=&region=&district=`, so Back walks up; old `?tab=` / `country=all` links still land), `usePlatformPlace` turns it into the level, the picks (an administrator's own unit fixes the levels above), their names, the ways down / up and «Boshqarish» (`setScopeUnit` + the admin panel). The list of the level is `buildEntries` (`platformModel.ts`): companies and countries from the tree with their numbers added (`CompanyCard` / `CountryCard`, a dashed `AddCard` — new company / add a country — and, at the top, the doorway to every company together, `company=all`, where a country card names the companies working there); regions, districts and facilities from `GET /platform/regions` completed with tree units that have no numbers yet, in `PlatformTable` (sortable, cards on a phone; the less needed columns step aside below `xl` / `2xl` so the table always fits its card). Above the list `PlatformSummary` — one quiet card: where and when with the period picker (`DateRangeFilter`), then six numbers in hairline-divided cells that follow the card's own width (2 / 3 / 6 in a row), sums short (`fmtMoneyShort`: «1,99 mlrd so‘m») with the exact amount and the meaning on hover, so nothing ever leaves its cell; below the list `PlatformTrend`; a search box once a list passes six, CSV of what is shown. What can be added sits where it belongs: «Yangi kompaniya» (`CompanyModal`, with its first country, then the page goes into it), «Davlat qo‘shish» (`CountryModal`, the company fixed when inside one), «Yangi muassasa» (the quick-start dialog opened under the company's unit of the place). A first-visit «Qanday foydalaniladi?» note is put away per browser (`clinic.platform.tip`).
- Catalog: `Category` (tree, `workflow`) → `ServiceType` (price, schemaId, defaultTemplateId, documentScope) → `AttributeSchema` (fields: text/longtext/number/select/multiselect/boolean/date/table).
- Orders: `Order` (number, patient, status, payment, totals, progress) → `OrderItem` (serviceType, status pending→entered→submitted→approved|rejected, `values: ValueMap`) → `ResultDocument` (templateId, deliveries).
- Templates: `ResultTemplate` (status draft/active/archived, serviceTypeIds/categoryIds, `doc: TemplateDoc` with absolute-px elements text/field/rect/ellipse/line/image/table). Rendering helpers in `domain/template-render.ts` (`interpolate`, `formatValue`, `fieldFlag`, `fieldReference`, `tableRows`).
- Messaging: `OutboxMessage` (sms outbox with scheduled/queued/sent/delivered/failed).

## Data layer (http)
`data/http/client.ts` — thin fetch client (`api.get/post/put/delete`, bearer token per actor staff|patient from localStorage, camelCase JSON, `ApiError` from the backend error envelope, `absoluteUrl()` for `/api/v1/files/*` and PDF links, 401 → `onUnauthorized` → auth store drops the session). Each `data/http/<x>.http.ts` implements one repository interface against `TibDaftari-Backend` (`ARCHITECTURE.md` there is the endpoint map). Accounts are created with the backend CLI (`create-country-root`, `create-superadmin`); patient OTP `devCode` is returned only when the backend runs in OTP dev mode.
